# 五服务器爬虫平台架构设计（完整平台版 + 分阶段落地版）

> 目标：在现有 `afu`、`deepseek`、`doubao`、`yuanbao` 四个爬虫基础上，设计一套完整的平台架构，支持 1 台主队列服务器 + 4 台消费者服务器，统一任务调度、账号生命周期管理、日志聚合、时间窗控制和队列策略控制。
>
> 说明：本文档采用“完整平台文档版 + 分阶段落地版”的写法。即：
>
> - 架构目标按完整五服务器平台设计；
> - 实施方式按当前代码基础分阶段落地；
> - 明确标注高风险点、不可行点、当前代码不支持点，避免把理想方案误认为可以直接稳定上线。

---

## 一、现状与问题

### 1.1 当前项目的真实结构

当前代码并不是统一平台，而是多个独立爬虫脚本的组合：

- `py_main.py`
  - 负责监听 MySQL 任务表；
  - 当前只统一调度 `deepseek` 和 `yuanbao`；
  - 通过 `AIModelParallelRunner` 做平台级并发。

- `afu/afu.py`
  - Selenium + Chrome Profile；
  - 自己轮询数据库、自己选择账号、自己执行、自己更新任务状态；
  - Profile 占用控制基于进程内 `_profiles_in_use`。

- `doubao/doubao.py`
  - Selenium + Chrome Profile；
  - 结构与 `afu.py` 类似；
  - 同样是本地 Profile + 本进程内占用锁。

- `deepseek/deepseek.py`
  - Playwright + Cookie 文件；
  - 当前以本地 cookie 文件轮换方式并发；
  - 没有统一账号表，也没有统一账号状态机。

- `yuanbao/yuanbao.py`
  - Playwright + Cookie 文件；
  - 当前同样是 cookie 文件轮换；
  - 没有统一账号生命周期控制。

### 1.2 当前代码的关键特征

当前实现的核心特点不是“平台化”，而是“脚本化”：

- 每个爬虫有自己的数据库查询逻辑；
- 每个爬虫有自己的任务状态更新逻辑；
- 每个爬虫有自己的账号轮换逻辑；
- 日志没有统一的结构化模型；
- 账号状态没有统一数据库表做权威来源；
- 主调度、账号调度、重试调度、失败回写目前没有集中收口。

### 1.3 当前痛点

1. 无统一调度中心，四个爬虫无法真正统一调度。
2. 无统一账号生命周期管理，停用账号、备用账号、成功恢复状态都无法跨任务持久生效。
3. 无统一任务主状态，任务状态容易被各脚本分别改写。
4. 多服务器部署后，状态一致性、重复消费、重复执行风险显著增加。
5. `afu` / `doubao` 的 Profile 资源是本地浏览器环境，无法像普通任务一样随意跨机器共享。
6. `deepseek` / `yuanbao` 的 cookie 文件当前仍是本地文件资源，不是平台资源。
7. 日志和告警可以做，但任务、账号、调度三者统一控制才是真正难点。

## 二、目标架构（完整平台版）

### 2.1 服务器角色划分

目标平台规划为 5 台服务器：

#### 主队列服务器

职责：

- 轮询 MySQL 任务表；
- 生成主任务队列；
- 按模型拆分子队列；
- 聚合消费者执行状态；
- 维护统一任务主状态；
- 维护账号主表和账号状态表；
- 管理调度策略（FIFO / LIFO / Priority）；
- 控制时间窗调度；
- 提供 FastAPI 后端接口；
- 提供日志查询入口、告警入口、平台控制入口。

#### 服务器 A

- 只部署 `afu.py` 对应消费者；
- 只消费 `queue:afu`；
- 只使用 AFu 对应的本地 Chrome Profile 资源。

#### 服务器 B

- 只部署 `deepseek.py` 对应消费者；
- 只消费 `queue:deepseek`；
- 只使用 DeepSeek 对应的本地 cookie 资源。

#### 服务器 C

- 只部署 `doubao.py` 对应消费者；
- 只消费 `queue:doubao`；
- 只使用 DouBao 对应的本地 Chrome Profile 资源。

#### 服务器 D

- 只部署 `yuanbao.py` 对应消费者；
- 只消费 `queue:yuanbao`；
- 只使用 YuanBao 对应的本地 cookie 资源。

## 三、任务模型设计

### 3.1 主任务与问题任务的关系

主队列中的“任务”并不是简单的一条数据库记录，而是“任务 × 问题 × 轮次”的执行单元。

建议抽象为两层：

#### 任务主记录

来自现有表 `ent_data_product_llm_task`：

- `ProductLlmTaskId`
- `ProductTaskId`
- `ProductId`
- `LlmKey`
- `MaxRounds`
- `Status`

#### 问题执行记录

由主队列调度器展开生成：

- `ProductLlmTaskId`
- `QuestionId`
- `QuestionName`
- `RoundNum`
- `DispatchStrategy`
- `Priority`
- `QueueName`
- `ServerId`
- `AccountId`
- `ExecuteStatus`

### 3.2 为什么主队列里要放“问题任务”而不是“任务表原记录”

因为实际执行单位不是一整条 `ProductLlmTaskId`，而是：

- 某个任务；
- 某个问题；
- 某一轮；
- 由某个账号在某台服务器上执行。

如果主队列只存任务主记录，消费者拿到后仍然需要自己拆问题、拆轮次、分账号，那么平台控制就失效了。

因此：

> 主队列必须以“问题执行单元”为最小调度粒度。

## 四、队列体系设计

### 4.1 队列层级

平台设计为两层队列：

#### 主队列（Master Queue）

作用：

- 存放所有待分发的问题执行单元；
- 是唯一统一入口；
- 由主队列服务器负责生成和分发；
- 控制调度顺序、优先级、时间窗。

#### 消费队列（Consumer Queue）

- `queue:afu`
- `queue:deepseek`
- `queue:doubao`
- `queue:yuanbao`

作用：

- 按爬虫模型拆分；
- 每台服务器只消费自己对应的队列；
- 消费者执行完成后回报 `queue:result`。

### 4.2 主队列与消费队列的职责边界

#### 主队列负责

- 从数据库生成问题执行单元；
- 根据 `LlmKey` 路由到不同消费队列；
- 按策略决定哪些任务先发；
- 决定是否允许继续拉新任务；
- 决定某个账号是否可用；
- 聚合执行结果并回写主状态。

#### 消费队列负责

- 只接收本机模型能执行的任务；
- 领取任务；
- 根据账号选择结果执行浏览器自动化；
- 回报成功 / 失败 / 异常 / 账号失败信息；
- 不再自己决定全局调度策略。

## 五、时间窗调度设计

### 5.1 业务规则

用户要求：

- 每天 **09:00 到 20:00** 允许跑任务；
- 超过时间后，消费者**不再从主队列取新任务**；
- 但已经进入本地消费队列、或已经被消费者领取的任务，必须先跑完；
- 不能在时间到达时强杀浏览器任务。

### 5.2 推荐实现方式

时间窗控制只作用于“是否允许继续领取新任务”，不作用于“是否强行终止当前任务”。

定义两个层级：

#### 主队列拉取开关

- `master_dispatch_enabled = true/false`
- 09:00 ~ 20:00：允许从数据库提取新任务并投递到消费队列
- 20:00 以后：停止继续向消费队列投递新任务

#### 消费者拉取开关

- `consumer_fetch_enabled = true/false`
- 09:00 ~ 20:00：允许从本消费队列继续领取任务
- 20:00 以后：停止从本消费队列继续拉任务
- 但当前已经领取到 worker 内存中的任务继续执行到完成

### 5.3 关键说明

时间窗不是“停服务”，而是“停领新任务”。

这必须明确写入文档，否则容易被误解为：

- 20:00 整个平台立刻空闲；
- 浏览器自动化能像普通接口一样瞬间停下。

实际并不能保证这一点。

## 六、调度策略设计

### 6.1 需要支持的策略

平台目标支持三类策略：

- FIFO：先进先出
- LIFO：后进先出
- Priority：高优先级优先

### 6.2 推荐策略模型

不建议三种策略在运行时自由混搭，而应抽象为：

#### 主策略

- `fifo`
- `lifo`
- `priority_fifo`
- `priority_lifo`

推荐默认使用：

> `priority_fifo`

含义：

- 先按优先级排序；
- 同优先级内再按创建时间先进先出。

### 6.3 为什么不能简单“都支持”

因为：

- 如果同一批任务既要 FIFO，又要允许后进后出，又要允许高优插队，实际就不是一个稳定规则；
- 会出现某些老任务永远得不到执行；
- 平台页面也无法正确解释为什么这个任务排在前面或后面。

因此文档中会明确：

> 同一时刻只能启用一个统一调度策略配置，不支持无规则混用。

### 6.4 优先级字段建议

建议新增：

- `PriorityLevel`: high / medium / low
- `PriorityScore`: 数值化排序字段（如 100 / 50 / 10）

若现有任务表没有优先级来源，则默认全部为 `medium`。

## 七、账号管理设计

### 7.1 账号数量与角色

当前设定：

- 正常账号：100 个
- 备用账号：50 个

这里的“账号”对于不同爬虫类型含义不同：

- `afu` / `doubao`：本地 Chrome Profile 账号资源
- `deepseek` / `yuanbao`：本地 cookie 文件账号资源

平台层必须统一抽象，不再把它们仅仅看作本地目录名或文件名。

### 7.2 账号状态定义

建议统一账号状态：

- `normal`：正常可用
- `running`：当前执行中
- `suspicious`：第一次失败后标记为可疑
- `abnormal`：第二次失败后标记为异常
- `disabled`：第三次失败后停用
- `backup`：备用账号

### 7.3 状态流转规则

根据用户要求，建议统一规则如下：

- 第一次失败：`normal -> suspicious`
- 第二次失败：`suspicious -> abnormal`
- 第三次失败：`abnormal -> disabled`
- 第四次重试：不再尝试原账号，而是从 `backup` 账号池取备用账号
- 任意一次成功：账号状态恢复为 `normal`，失败计数清零

### 7.4 核心业务原则

平台必须满足以下原则：

1. 每次调度前先查账号表；
2. `disabled` 状态账号绝不能再次进入分配池；
3. `backup` 账号不能和正常账号混用，应只在正式账号达到停用条件后启用；
4. 账号成功一次，必须把历史失败状态恢复；
5. 账号状态必须持久化到数据库，而不是放在进程内存里；
6. 平台不能只根据“cookie 文件存在”或“profile 目录存在”来判断账号可用。

### 7.5 推荐账号表设计

#### 账号主表

```sql
CREATE TABLE crawler_accounts (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    crawler VARCHAR(32) NOT NULL,
    account_id VARCHAR(128) NOT NULL,
    account_type VARCHAR(16) NOT NULL,      -- primary / backup
    account_source VARCHAR(16) NOT NULL,    -- profile / cookie
    resource_path VARCHAR(255) NOT NULL,
    status VARCHAR(16) NOT NULL,            -- normal / running / suspicious / abnormal / disabled / backup
    fail_count INT DEFAULT 0,
    last_success_time DATETIME NULL,
    last_fail_time DATETIME NULL,
    last_fail_reason VARCHAR(255) NULL,
    server_id VARCHAR(32) NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_crawler_account (crawler, account_id)
);
```

#### 账号事件表

```sql
CREATE TABLE crawler_account_events (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    crawler VARCHAR(32) NOT NULL,
    account_id VARCHAR(128) NOT NULL,
    task_id VARCHAR(64) NULL,
    event_type VARCHAR(32) NOT NULL,        -- success / fail / disable / recover / switch_backup
    old_status VARCHAR(16) NULL,
    new_status VARCHAR(16) NULL,
    fail_count INT DEFAULT 0,
    message VARCHAR(255) NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

### 7.6 为什么账号表是刚需

如果没有统一账号表，当前代码会出现这些问题：

- 本次任务里把某个账号判定为停用，但下次脚本启动时仍可能再次选中；
- 一个爬虫脚本里失败计数是内存变量，进程一重启就丢；
- 四个爬虫都自己做账号轮换，平台无法统一查看“到底哪些账号已经废了”；
- 备用账号无法真正被平台统一接管，只能变成脚本内部临时替换。

## 八、任务主状态设计

### 8.1 为什么需要主状态

在完整平台里，任务状态不能由单个爬虫脚本自己定义，因为：

- 任务先进入主队列；
- 再进入消费队列；
- 再被某个消费者领取；
- 再由浏览器执行；
- 再回写数据库。

如果没有统一主状态，平台页面看到的是一套，数据库里是另一套，爬虫日志里又是第三套。

### 8.2 建议主状态生命周期

- `pending`：数据库已发现，但尚未进入主队列
- `queued`：已进入主队列
- `dispatched`：已分发至模型消费队列
- `claimed`：已被消费者领取
- `running`：浏览器自动化执行中
- `completed`：执行成功并已回写结果
- `failed`：执行失败
- `retry_waiting`：等待重试
- `stale`：消费者失联或超时
- `cancelled`：人工取消

### 8.3 主状态的权威来源

建议原则：

- **平台主状态表** 是权威来源；
- 现有 `ent_data_product_llm_task.Status` 仍保留，但只作为业务表同步字段；
- 不允许四个爬虫继续直接把主任务表当成自己的唯一状态来源。

## 九、日志与告警设计

### 9.1 日志策略

延续当前方案：

- 各服务器本地文件日志；
- 腾讯云 CLS 统一采集全文日志；
- MySQL 只保存关键摘要；
- 平台页面展示任务摘要和 CLS 查询入口。

### 9.2 告警策略

建议至少支持：

- 账号连续失败告警；
- 账号停用告警；
- 备用账号接管告警；
- 消费者失联告警；
- 主队列积压告警；
- 执行时间过长告警；
- 结果回写失败告警。

## 十、高风险点与不可行点（必须明确）

这一章是本方案最重要的现实约束说明。

### 10.1 分布式状态不可能天然一致

即使平台设计了主状态表、Redis 队列、结果回写，也仍然会存在以下场景：

- 主队列已经分发，但消费者回报丢失；
- 消费者已经执行成功，但主状态仍停留在 `running`；
- MySQL 回写成功，但 Redis 状态未更新；
- 某个任务因为网络问题被重复分发。

因此：

> 该平台只能做到“尽量收敛状态”，不能保证绝对实时一致。

### 10.2 网络抖动会造成重复消费风险

在分布式架构下，只要发生以下情况，就可能导致同一任务被重复执行：

- Consumer 已经领取任务，但心跳上报失败；
- 主队列服务器误判消费者失联；
- 任务被重新投递；
- 另一台消费者又领取了同一个任务。

对于浏览器自动化爬虫，这种重复执行比普通业务任务更危险，因为会带来：

- 重复写库；
- 重复登录；
- 账号异常；
- 代理异常；
- 页面风控触发。

### 10.3 AFu / DouBao 的 Profile 不是中心化资源

当前 `afu.py` 与 `doubao.py` 的资源模型是：

- 本地磁盘上的 Chrome Profile 目录；
- 进程内 `_profiles_in_use` 集合做占用锁。

这意味着：

1. Profile 占用锁只在本进程内有效；
2. 无法天然跨服务器共享；
3. 无法像数据库记录一样统一调度；
4. 如果要平台化，必须把 Profile 资源登记到账号表，且明确绑定所属服务器。

因此：

> `afu` / `doubao` 的账号资源不能像普通队列消费者一样跨服务器自由迁移。

### 10.4 DeepSeek / YuanBao 的 cookie 当前只是文件，不是账号系统

现在 `deepseek.py` 与 `yuanbao.py` 的调度逻辑是：

- 扫描本地 cookie 文件；
- 随机打乱；
- 循环轮换；
- 失败后切换到另一个 cookie 文件。

这不等于统一账号系统。

如果不引入账号表，那么：

- 停用账号无法在下一次调度时真正失效；
- 备用账号无法按规则接管；
- 成功恢复正常状态无法持久化；
- 平台页面看到的账号状态永远是不准确的。

### 10.5 时间窗不能理解成“立即停机”

超过 20:00 以后，消费者只能停止继续取新任务，不能立即终止当前浏览器自动化。

原因：

- 浏览器自动化执行中断可能导致：
  - 页面残留；
  - 登录状态损坏；
  - 数据未写回；
  - 任务半成功半失败。

因此文档必须明确：

> 时间窗控制的是“停止拉新”，不是“强制终止正在运行的爬虫”。

### 10.6 当前代码并不支持“直接切换到完整平台”

现有代码是“各爬虫自己调数据库、自己选账号、自己跑任务、自己改状态”的脚本体系。

如果不先拆掉这些职责，平台只是外面多了一层壳：

- 主队列在调度；
- 各爬虫也在自己查库；
- 结果会互相打架。

因此：

> 当前代码基础不能直接稳定支撑完整平台，需要先做职责收口与执行入口改造。

## 十一、分阶段落地方案（明确分阶段）

完整平台目标不等于一次性上线。应按下面路线推进。

### 阶段 A：统一任务入口

目标：先解决“谁负责取任务”。

做法：

- 由主队列服务器统一轮询 MySQL；
- 四个爬虫停止自己轮询“未开始”任务；
- 主队列把问题执行单元统一生成。

产出：

- 四个爬虫变为“只接收外部任务”的执行器；
- 平台成为唯一调度入口。

### 阶段 B：消费队列拆分

目标：把四个爬虫真正接入统一平台。

做法：

- 拆分 `queue:afu / queue:deepseek / queue:doubao / queue:yuanbao`；
- 每台服务器只消费自己的模型队列；
- 结果统一回报主队列服务器。

产出：

- 五台服务器的基本调度链路；
- 基础主状态流转；
- 时间窗停拉新能力。

### 阶段 C：账号主表接管

目标：把账号从“本地文件名 / 目录名”变成“平台资源”。

做法：

- 建立账号主表、账号事件表；
- 停用账号不再参与调度；
- 备用账号按规则接管；
- 成功恢复正常状态；
- 所有分配前必须先查账号表。

产出：

- 账号生命周期持久化；
- 账号状态面板基础能力；
- 停用账号不会再次被误用。

### 阶段 D：调度策略平台化

目标：把 FIFO / LIFO / Priority 真正放入平台配置。

做法：

- 主调度服务统一实现策略排序；
- 队列层不再各自定义排序方式；
- 新增优先级字段和默认规则。

产出：

- 可控的任务顺序；
- 平台页面可解释的排队逻辑。

### 阶段 E：平台能力增强

目标：补齐平台可观测与运营能力。

做法：

- 腾讯云 CLS 日志聚合；
- 告警面板；
- 账号状态面板；
- 队列面板；
- 人工启停和策略调整能力。

产出：

- 领导需要的“平台”外观与基本管理能力；
- 但底层风险仍需长期治理。

## 十二、当前代码必须改的地方

这一章不是“可选优化”，而是如果要做完整平台，必须面对的改造点。

### 12.1 `py_main.py` 需要改什么

当前问题：

- `py_main.py` 只调度 `deepseek` / `yuanbao`；
- 仍然是直接查数据库、直接分组、直接调用爬虫函数；
- 不是主队列服务器。

必须改成：

- 主队列调度服务；
- 统一从数据库取任务；
- 展开为“问题执行单元”；
- 根据 `LlmKey` 投递到对应消费队列；
- 维护主状态表；
- 接收各消费者结果回报。

结论：

> `py_main.py` 不是小改，而是职责重做。

### 12.2 `afu/afu.py` 需要改什么

当前问题：

- 自己查数据库；
- 自己更新任务状态；
- `_profiles_in_use` 只是进程内锁；
- 不支持平台下发任务；
- 不支持统一账号表判定。

必须改成：

- 只接收消费者下发的单个执行任务；
- 账号分配改为先查账号表；
- Profile 使用前后要向平台回报状态；
- 不再自己批量扫描“未开始”任务；
- 本地 `_profiles_in_use` 只能作为补充防撞，不再作为平台级占用依据。

结论：

> `afu.py` 要从“独立脚本”改成“可被平台调用的执行器”。

### 12.3 `doubao/doubao.py` 需要改什么

与 `afu.py` 类似，必须改：

- 去掉自己轮询数据库入口；
- 去掉脚本内部的全局任务分发职责；
- 统一接入平台账号表；
- Profile 绑定服务器；
- 失败计数不能只靠进程内变量；
- 成功后恢复状态必须回写数据库。

### 12.4 `deepseek/deepseek.py` 需要改什么

当前问题：

- 以本地 cookie 文件轮询方式分配任务；
- 自己切换 cookie 重试；
- 没有账号主表；
- 没有停用账号持久控制。

必须改成：

- 消费者先从账号表选账号；
- cookie 文件只作为账号资源路径；
- 当前账号失败次数由数据库维护；
- 达到停用阈值后不能再次被选中；
- 第四次重试切换到备用账号，而不是继续随便轮换 cookie 文件。

结论：

> `deepseek.py` 需要从“文件轮询”改成“账号状态机驱动”。

### 12.5 `yuanbao/yuanbao.py` 需要改什么

与 `deepseek.py` 同类问题，必须改：

- cookie 文件扫描逻辑不能再直接决定账号调度；
- 必须平台先查账号表再分配；
- 停用账号不能再参与循环；
- 备用账号必须有独立标识和接管规则；
- 当前的错误计数器需要数据库持久化。

### 12.6 `shared-methods/shared_methods.py` 需要改什么

当前问题：

- 既有数据库配置，又有代理配置，又有日志和告警工具；
- 仍偏向脚本共享工具，而不是平台基础设施配置层。

建议改造：

- 拆分配置：数据库、代理、日志、告警分离；
- 代理配置不要继续以硬编码方式散落在共享工具里；
- 为平台服务提供统一配置入口。

### 12.7 `database_usage_example.py` 需要改什么

当前问题：

- 主要面向结果写库；
- 不包含平台化账号表、任务事件表、账号事件表、主状态表写入逻辑。

必须补充：

- 账号状态更新接口；
- 账号失败计数更新接口；
- 账号事件记录接口；
- 任务主状态事件记录接口；
- 重试结果回写接口；
- 消费者执行事件摘要写入接口。

## 十三、明确哪些地方“很难稳定实现”

这部分是写给决策者看的，不是推脱，而是说明工程边界。

### 13.1 最难的不是页面，而是状态收口

前端平台、日志平台、告警平台都能做。

真正难的是：

- 任务状态是否一致；
- 账号状态是否一致；
- 哪个账号此刻能不能用；
- 某个任务是不是已经被另一台机器领取；
- 某个任务失败后到底是该重试、换账号、还是停用账号。

### 13.2 `afu` / `doubao` 的 Profile 机制天然不适合做成自由分布式资源

这类资源本质上是：

- 本地浏览器环境；
- 有历史登录态；
- 有本地缓存；
- 有风控痕迹；
- 不能像普通消息消费者一样随意迁移。

所以平台虽然可以调度“任务去哪个模型”，但不能把某个 Profile 当成全平台共享资源自由漂移。

### 13.3 账号状态管理会显著增加数据库查询压力

用户要求的账号生命周期意味着：

- 每次分配前查账号表；
- 每次失败更新账号状态；
- 每次成功恢复账号状态；
- 每次备用切换写入事件；
- 下次分配还要过滤停用账号。

这会让数据库不再只是“存结果”，而是变成“调度权威中心”，必须重新考虑连接、索引、并发和事务边界。

### 13.4 时间窗、优先级、账号状态三者叠加后，调度逻辑会非常复杂

例如：

- 高优任务来了，但当前时间已过 20:00；
- 低优任务已在消费队列中；
- 正常账号已停用，只剩备用账号；
- 备用账号也只允许某个模型使用；
- 当前队列策略又设成了 LIFO。

这些都不是“多写几个 if”能稳妥解决的问题，需要统一调度规则和严格测试。

## 十四、推荐的结论

### 14.1 可以做的

可以形成一份完整的五服务器平台方案，并分阶段落地：

- 主队列服务器；
- 四个消费者服务器；
- 时间窗控制；
- 调度策略控制；
- 账号生命周期管理；
- 日志和告警平台。

### 14.2 不能误解的

但必须明确：

1. 这不是在当前脚本基础上“加个页面”就完成的；
2. 这本质上是把脚本体系改造成平台体系；
3. 账号、状态、调度三者必须统一收口，否则平台只是表面平台；
4. `afu` / `doubao` 的 Profile 模式决定了它们不能像普通任务那样自由分布式共享；
5. 平台可以做，但短期不能承诺“天然稳定”。

### 14.3 实施建议

建议实际推进顺序是：

1. 先做主队列统一入口；
2. 再拆四个消费者；
3. 再做账号表接管；
4. 再做策略控制；
5. 最后做可视化平台和日志完善。
